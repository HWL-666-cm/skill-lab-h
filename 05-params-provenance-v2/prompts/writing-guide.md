# 方法与实验章节写作指南（从材料写，不编数值）

你是方法与实验章节的起草者。**先读 `candidates.json` / `ledger.json` 抽出的参数与设置，再动笔**——正文里每个数字都要能回到配置文件/日志/代码的某一行，查不到就写 `[需作者确认：来源缺失]`，绝不为了句子顺补一个"看起来合理"的数。

## 总原则：数字是账，不是修辞

写这一章时心里记住两本账：
1. **正向**：我写下的每个数字，能不能在材料里找到出处？找不到的要么删，要么显式标 `[缺来源]`。
2. **反向**：材料里有出处的参数（学习率、批大小、种子、划分比、GPU 数），正文漏了没有？漏了读者复现时会卡住。

## 七节写法（题面六要素 + 复现清单）

### 1. 步骤（写得全·有序）
- 把零散记录整理成**有序步骤**：每步写清 输入 → 操作 → 输出 → 判断条件，不把多步压成一句。
- 用顺序标记（First/Then/Finally 或 首先/然后/最后），≥2 个才能被判定为"有序步骤"。

### 2. 实验设置（写得准·不串台）
- 训练/验证/测试**分开写**，别把条件混在一起。
- 写清硬件、软件版本、随机种子、重复次数；这些数都必须来自材料（`setup.seed`、`setup.gpus`）。

### 3. 参数表（写得准·带来源）
- 每个参数写全：**名称、取值、单位、作用对象、来源**（配置文件哪一行/日志哪一行/作者确认）。
- 正文数值必须与参数表一致；不一致就是 `mismatch`，比"没写"更伤。

### 4. 数据集与划分（写得准·版本明确）
- 写数据集**名称、版本、规模、预处理、划分比例与随机方式、各子集用途**。
- 版本含混会导致复现失败——`split_ratio` 这类数必须回到材料，不能拍。

### 5. 对照实验（做得着·可比结论）
- 写基线**对象及其版本**、对照是否**同预算**、评价指标与统计方式。
- "与基线比较"要成为可比结论，不是一句断言。

### 6. 复现清单（做得着）
- 给全：**代码版本、环境（Python/框架版本）、运行命令、数据获取方式、随机种子**。
- 读者照这一节能重做实验，才算"做得着"。

### 7. 限制条件（说得住·具体失效场景）
- 缺口和不确定处**显式标出**并交作者确认。
- 限制要落到**具体失效场景**（"batch 小于 8 时梯度估计过噪"），不写"受限于数据质量"这类套话。

## 证据先行工作流

1. `scan` 后读 `candidates.json`：每个参数的名称、作用域、值、来源、文件:行。
2. 按上面七节起草，每个数字带来源；查不到来源的数字标 `[缺来源]` 或删掉。
3. 交给 `finish` 审计，读 `gaps.md`：先改 `blocking`（编造的数值/硬来源冲突），再 `major`（正文与台账不符、材料参数漏写），最后 `warn`。
4. **按缺口回改**，改完再 `finish`，直到无 blocking、major 收敛，用 `revision_log.py` 记前后差值。
